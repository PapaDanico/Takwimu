# Backup and restore

Takwimu has no database and no user data. Everything needed to rebuild the site is in git: code, `data/`, `schemas/`, the source manifest with SHA-256 of cited documents. The built site is regenerated by `npm run build`. Two independent copies exist:

1. **Git** (GitHub `PapaDanico/Takwimu`, branch `claude/eager-rubin-7bpcgq`, plus every local clone). This is the backup of record.
2. **Netlify deploys.** Every deploy is immutable and stays in the site's deploy history, so any earlier version can be published again without a rebuild.

Source PDFs are not redistributed (licences: link and cite only); they are re-obtainable from the publisher or the Parliament library, and their hashes in `data/source-manifest.json` and `data/source-library.json` prove the copy is the one that was read.

## Drill: restore from git

`bash scripts/ops/backup-drill.sh [branch]` clones the pushed branch from GitHub into a new temp directory, exports the same commit from the local repository with `git archive`, runs `npm ci` and `npm run build` (every build gate) in both, and compares the SHA-256 of every built data file in `dist/data/` (the `/data/` page's own `index.html` and `index.txt` are excluded: they carry Next's per-build id). PASS means GitHub alone reproduces the published data byte for byte. It never deploys and never reads uncommitted files. Run it quarterly and before any major release.

## Restore production on Netlify (previous deploy)

Use when a release is bad or the live site was changed unexpectedly. Deploys are immutable, so this restores the exact earlier bytes.

1. Find the last good deploy id in `docs/production-provenance.md` (for example `6b01a551da2509deb5134cc9`, commit 3e8efd3).
2. Dashboard: Netlify > Sites > takwimu > Deploys > open that deploy > **Publish deploy**.
3. Or API: `POST https://api.netlify.com/api/v1/sites/bf11e227-c98e-4258-aff6-d7660459aef1/deploys/<deploy_id>/restore` with a personal access token, or `netlify api restoreSiteDeploy --data '{"site_id":"bf11e227-c98e-4258-aff6-d7660459aef1","deploy_id":"<deploy_id>"}'`.
4. Verify as in `docs/ops/release-checklist.md` section 5 (pages, redirects, live `/data/*.json` hashes against that commit's build).
5. Record the restore (date, deploy id, reason) in `docs/production-provenance.md`.

## Restore from git (Netlify history lost, or new site)

1. `git clone --branch claude/eager-rubin-7bpcgq https://github.com/PapaDanico/Takwimu`; check out the commit recorded as live in `docs/production-provenance.md`.
2. `npm ci && npm run build`, then the gates in `docs/ops/release-checklist.md` section 2.
3. Upload a clean `git archive` of that commit to the Netlify site (production comes from this branch by CLI upload, never from `main`; see `docs/architecture-map.md`). If the remote build fails intermittently, use the prebuilt fallback in `docs/ops/monitoring.md`.
4. Compare live `/data/*.json` hashes with the local `dist/data/`, then record the deploy.

## If git were lost

Any developer clone is a full copy (`git clone --mirror` to a new remote restores all branches and history). The source documents can be re-acquired from the URLs in the source library; `scripts/ops/check-sources.js` reports which are still reachable and whether their bytes still match the recorded hashes.
